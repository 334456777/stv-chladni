# 删掉注释和文档里多余和误导的句子

注释和文档只写现状，写成最终结论；经过和改动前后的对比写进交给用户的说明，不留在代码和 README 里。这里是判断一句话该删还是该留的标准，以及把全部注释和文档读一遍的步骤。

## 范围

- 代码注释：`src/` 下 Rust 的 `///`、`//!` 和普通注释，`src/gpu/*.wgsl` 着色器的注释，`Cargo.toml` 的 `#` 注释，skill 脚本里的注释和文档字符串。
- 命令行帮助：`src/main.rs` 里 clap 参数上的 `///` 会原样显示在 `stv <子命令> --help` 里，按注释读。
- 界面文字：`src/gui.rs` 里的标签、提示和报错，按面向用户的文字读。
- 文档：`README.md`、`.claude/skills/` 下的 skill。
- `vendor/` 是第三方代码，不改；只看 stv 自己加的注释（`vendor/gpu-allocator/Cargo.toml` 末尾以 `# stv：` 开头的几行）。

## 要删的

按读者的需要判断：删掉这句以后，改这段代码或照着做的人少知道了什么？什么都没少，就删。常见的有下面几类。

### 复述需求

提需求时的说法、比喻或来源留在了文字里，读者从中得不到程序做什么：

- 「像参考视频那样」「类似某软件的效果」：写这个功能本身是什么样。
- 强调这是有意的：「这是设计如此」「是正式的，不是暂用的」。写明它做什么就够了。
- 按谁的要求：「按用户要求」「用户希望」。

### 经过和前后对比

文字说的是写下它时发生了什么，不是现在的代码：

- 「原来」「改为」「已删除」「不再」「以前」：删掉指向旧行为的部分，只留现状。同一段里指前一步的说法（如测试里的上一个断言）不属于这一类。
- 「本次」「这次改动」「修复后」：注释和文档里没有「这次」。
- 写下时正确、现在已经不成立的说明（如写着「新沙从画面上方落下」，代码已经是从振动板正上方按透视落下）：改成现状。

### 排查碰壁后留下的警告和经验

排查时走过的弯路、某一次遇到的现象，写成了给后来者的提醒：

- 试过但不对的方向，如「先试了 Vulkan 的 Fifo，帧率还是 500 多」：结论（为什么选 DX12）留下，经过删掉。
- 只在一次排查里出现、已经修好或不会再遇到的现象：某次测试的读数、已修复问题的绕过办法、某个工具一次性的故障。
- 泛泛的自我提醒：「凭记忆写的表可能有错」「注意别弄错」。
- 为一次排查写的测试或诊断代码的说明，只交代了当时的用意：改写成它做什么、输出什么。

### 稻草人

否定一个读者本来不会采用的做法，或者正确的做法已经写明，又补一句反面：

- 「用 realfft 计算频谱，不自己写 FFT」：正确的做法已经写了，后半句删掉。
- 「不要手改 X」「不是驱动的问题」：没有人会这样做，或者是在回应某一次具体的误判。
- 判断方法：被否定的做法是读者顺手就会做的吗？是，而且后果不明显，那是坑，保留并写明后果；不是，就删。

### 计划和过时的引用

- 没有兑现的打算：「以后会……」「TODO：之后支持……」。
- 引用已经不存在的文件、函数、常量、命令或参数（改名或删掉之后留下的旧名字）。

## 要留的

下面这些看起来像上面几类，但不删：

- 原因：「不这样做时……会失败」。它说明代码为什么是这样，如界面优先选 DX12 的原因、`vendor/gpu-allocator` 固定 windows 版本的原因；用了过去时也是原因，不为改时态单独改。
- 会反复遇到的坑：自然的做法在不明显的地方出错，写成「做 X 时会 Y，因此 Z」。
- 规则和约束，包括写成否定句的：「必须与 xx 中的常量一致」「录制中不允许切换音源」。
- 面向用户的警告和报错的处理办法（麦克风无数据、硬件静音、ffmpeg 找不到等提示）。
- 界面里的术语和名称：先在代码里核对是不是界面上的叫法，不当成错字改。
- 作者写的标语和带个人风格的句子：不改，列出来交给作者决定。

## 对话里的内容

注释和文档只写结果，以及理解结果所需的上下文，不写讨论的经过：

- 不写「用户要求」「按讨论」「我先试了」「前面提到的」。
- 选择的原因写成原因本身（「DX12 交换链能同步到显示器刷新率」），不写是谁、在哪次讨论里决定的。
- 不用讨论中临时起的、代码里没有的说法和代号。

## 逐条读完

关键词扫描只能找到有固定说法的经过和对比：

```sh
rg -n "原来|改为|改成|不再|以前|之前|本次|这次|修复|用户|按要求|TODO|以后" src README.md Cargo.toml .claude
```

复述需求、稻草人和碰壁的经验没有固定的词，只能逐句读。清理全部文字时：

1. 运行 [`scripts/list_comments.py`](scripts/list_comments.py)，列出项目自己的源文件的注释（跳过 `target/`、`vendor/`、`out/`）。输出分成几份，每份约 64 KiB，一条注释一行，连续的注释行合成一条：

   ```sh
   python .claude/skills/stv-trim-prose/scripts/list_comments.py target/trim-prose
   ```

2. 一份一份读完。每读完一份，在 `target/trim-prose/findings.md` 里记下结果：`文件:行`、原句、删掉还是改成什么、属于哪一类；没有就写「无」。中断后可以接着读，也不会漏掉某一份。
3. 整篇读 Markdown（`README.md`、各个 skill）和界面文字（`src/gui.rs` 里的字符串），再看一遍 `vendor/gpu-allocator/Cargo.toml` 末尾 stv 加的注释。
4. 同一类句子查遍所有位置后一起改，不逐处停下来问。只改属于上面几类的句子，其他措辞不顺手改，免得改动散到整个项目。
5. 改完删掉 `target/trim-prose/`。

## 改的时候

- 只动文字，不动代码。删掉整句或句中的从句后，把这一段重读一遍：语句要通顺，剩下的内容仍要说清这一项做什么。
- 文档注释不能删空：删到没有内容时改写成它做什么。
- 同一个说法也写在 README、命令行帮助或界面文字里时，一起改。
- 要删的内容是别处没有的结论时，先把结论补到它该在的地方（README 或对应的文档注释），再删。

## 检查

- `cargo clippy --release --all-targets`、`cargo test --release`、`cargo build --release`。
- 改了 WGSL：着色器在创建管线时才编译，跑一次短的无头渲染确认管线能建起来，再删掉输出：

  ```sh
  target/release/stv render <音频文件> --duration 1 -o target/trim-check.mp4
  ```

- 改了命令行帮助：看一遍 `stv <子命令> --help`。
- 最后按类列出删了什么、改成了什么、留了什么和留下的理由，交给作者逐条核对。

## 写新文字时

写的时候就用同样的标准，以后不必再清理：

- 注释写这段代码做什么、为什么这样做（不这样做会怎样），不写怎么发现的、试过什么、改之前是什么样。
- 排查的经过、改动前后的对比写进交给用户的说明，不写进注释和 README。
- skill 的坑只写会反复遇到的；只在一次排查中遇到、已经修好的不写。
- 写完用上面的扫描命令查一遍，再对照[要删的](#要删的)几类把新增的句子读一遍。
